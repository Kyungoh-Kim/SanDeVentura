# SanDeVentura — 부정적 피드백 및 개선 방향

> 현재 MVP 구조를 비판적으로 검토하고, 우선순위 있는 개선 방향을 제안합니다.

---

## 1. 콜드 스타트 문제 — 가장 치명적인 구조적 약점

### 문제

SanDeVentura의 핵심 가치인 "경로 안내"는 canonical trail이 존재해야 작동합니다. 그런데 canonical trail을 만들려면 먼저 사용자가 해당 산을 여러 번 다녀와야 합니다. 즉, **앱이 유용해지기 위해서는 앱이 이미 사용되고 있어야 하는** 순환 의존 구조입니다.

- 산 1개의 경로 신뢰도 0.8 달성에 필요한 추정 세션: 10~20개
- 활성 사용자 1명이 같은 산을 방문하는 평균 빈도: 월 1~2회
- 신뢰도 0.8 달성까지 걸리는 최소 기간: 5~10개월 (단독 사용자 기준)

**결과:** 초기 사용자는 "경로 데이터 없음" 메시지만 보다가 앱을 삭제할 가능성이 높습니다.

### 개선 방향

**단기:**
- 인기 등산로 (북한산 백운대, 설악산 대청봉 등 상위 10개 코스) 공개 GPX 데이터(국가산림공단, OpenStreetMap)로 초기 seed canonical trail 구성
- 신뢰도 낮은 seed 데이터임을 UI에 명시 ("참고용 경로, 정확도 제한")

**중기:**
- 운영자가 특정 코스에 GPX 파일을 직접 업로드해 canonical trail을 수동으로 초기화하는 기능
- 사용자 기여 세션이 쌓이면 자동으로 seed를 사용자 데이터로 교체

## 2. GPS 정확도 한계 — 핵심 기능의 신뢰성 위협

### 문제

snap-position 임계값은 현재 25m (경로 위) / 50m (이탈)로 설정되어 있습니다. 그러나:

- 수목 밀도 높은 산림 구간: GPS 오차 15~30m 일반적
- 깊은 계곡, 암벽 옆: GPS 오차 30~50m까지 증가
- **25m 임계값이 GPS 오차 자체와 겹치는 상황** → 경로 위에 있어도 이탈 경고 발생

유즈케이스 3의 시나리오가 실제 발생하며, 임계값 조정만으로는 구조적 해결이 불가합니다.

### 개선 방향

**단기:**
- rejected_track_points 데이터를 활용한 구간별 GPS 품질 지도 생성
  → "이 구간은 GPS 오차가 큰 구간입니다" UI 알림 추가
- 이동 평균(moving average) 필터를 snap-position에 적용: 1포인트가 아닌 최근 5포인트 평균 좌표로 판단

**중기:**
- 기압계(barometer) 기반 고도 데이터를 GPS와 융합 (Android API 지원)
  → 수직 이동 패턴으로 GPS 오차 보정
- Kalman filter 도입으로 track_points 기록 단계에서 노이즈 사전 제거

## 3. 운영자 단일 의존 구조 — 확장성과 거버넌스 부재

### 문제

현재 모든 백엔드 판단 (임계값 조정, 재추론 트리거, 품질 평가)이 개발자 1명(운영자)에게 집중되어 있습니다.

- canonical trail의 잘못된 경로를 사용자가 신고할 방법 없음
- 경로 오류가 발생해도 운영자가 알기 전까지 모든 사용자가 오경보 받음
- MVP = 운영자가 곧 제품이라는 구조 → 규모 확장 불가

### 개선 방향

**단기:**
- 모바일 앱에 "이 경로가 이상합니다" 간단 신고 버튼 추가
  → `mvp_events` 테이블에 기록, 운영자 대시보드에 신고 카운트 노출

**중기:**
- 신뢰 사용자(파워유저)에게 경로 검토 권한 부여 (커뮤니티 검수 모델)
- 사용자 기여 점수 시스템으로 데이터 품질 기여 인센티브 설계

## 4. 프라이버시-기능 트레이드오프 — 오버슈팅된 보수성

### 문제

"운영자는 raw 경로 열람 불가"라는 설계 원칙은 프라이버시 보호 측면에서 옳지만, 현재 구현이 지나치게 보수적입니다.

- canonical trail 이상 감지 시 운영자가 어느 구간이 문제인지 지리적으로 특정하기 어려움
- rejected_track_points의 좌표는 DB에 있지만 대시보드에서 시각화 불가
- 결과적으로 오류 원인 분석에 불필요하게 오랜 시간이 걸림

운영 효율을 위한 "집계 수준의 지리적 시각화"는 프라이버시 침해가 아닙니다.

### 개선 방향

**단기:**
- 운영자 대시보드에 "GPS 품질 열지도(heatmap)" 추가
  → 개별 사용자 식별 불가능한 셀 단위 집계 (H3 resolution 11, ~25m 육각형 셀 활용)
  → "이 구간에서 거부 포인트가 집중됨" 시각화

**중기:**
- 개인정보 보호 영향 평가(PIA) 기준으로 데이터 노출 정책 명문화
- 집계 레벨(H3 셀 단위, resolution 11 ~25m) vs 원시 레벨(좌표 단위) 접근 권한 분리

## 5. 테스트 및 검증 체계 부재 — 기술 부채

### 문제

현재 코드베이스에는 자동화 테스트가 사실상 없거나 최소화되어 있습니다.

- route_inference.ts (24KB)는 알고리즘의 핵심이지만 단위 테스트 없음
- validation.ts 검증 로직 변경 시 회귀 위험 감지 불가
- Edge Function 로직은 로컬 Supabase에서 수동 테스트에 의존

**리스크:** Sprint 9 이후 품질 강화를 진행할수록 이전 기능의 회귀 가능성이 누적됩니다.

### 개선 방향

**단기 (가장 높은 ROI):**
- route_inference.ts 알고리즘에 대한 입력/출력 기반 단위 테스트 5~10개
  (알려진 GPS 트레이스 → 예상 canonical trail 검증)
- validation.ts: 경계값(boundary) 케이스 테스트 (정확도 14.9m, 15.0m, 15.1m)

**중기:**
- Supabase Edge Function integration test (Deno test runner)
- CI/CD에 자동 테스트 파이프라인 추가 (.github/workflows)

---

## 6. 사용자 획득 전략 부재 — 제품보다 중요한 문제

### 문제

아무리 기술적으로 잘 만들어진 앱이라도, 콜드 스타트 문제와 맞물려 초기 사용자 획득 전략이 없으면 선순환 구조가 만들어지지 않습니다.

현재 문서(PRD, 포트폴리오 문서)는 기술 구현에 집중되어 있고, GTM(Go-to-Market) 전략이 없습니다.

- 등산 커뮤니티(산사랑, 클라이밍 커뮤니티)에서의 바이럴 전략 미정
- 초기 seed 사용자(데이터 기여자) 모집 방법 미정
- "내가 기여한 경로가 다른 사람에게 도움이 됐다"는 피드백 루프 UI 미구현

### 개선 방향

**단기:**
- 내 기여 현황 UI: "당신의 데이터가 N명에게 경로 안내를 제공했습니다"
- 특정 등산 동호회/커뮤니티 1~2곳과 파트너십 (초기 데이터 기여자 확보)

**중기:**
- 경로 기여자 배지 또는 감사 메시지 (게이미피케이션 최소화)
- 오픈소스 데이터 기여 모델 고려 (내 GPS 데이터를 공공 등산 DB에도 기여)
